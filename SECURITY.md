# Security

## Reporting a vulnerability
Please do not open a public issue. Email the ASZDA team (set up a dedicated address such as
`security@<your-domain>` before launch) with steps to reproduce. We aim to reply within 3 business days.

## Security model

### Identity and sessions
- Passwords hashed with **Argon2id** (`argon2-cffi`); minimum 10 characters, simple, explainable rules.
- Login answers the same way for unknown emails and wrong passwords; a dummy hash equalises timing.
- **Access tokens**: JWT (HS256), 15 minutes, kept in browser memory only.
- **Refresh tokens**: random 256-bit values, stored only as SHA-256 hashes, single-use (rotation),
  reuse revokes the session (a 20-second grace window allows two browser tabs to refresh at the same moment). Cookie: `HttpOnly`, `Secure` (production), `SameSite=Strict`, `Path=/api/auth`.
- **CSRF**: cookie-based endpoints also require the `X-Requested-With: aszda` header, which a
  cross-site page cannot send without a CORS preflight that the API does not allow.
- Each request re-checks the session row, so sign-out, password change and deactivation take
  effect immediately.
- Email verification and password-reset tokens are single-use, hashed, and expire (48 h / 60 min).

### Authorization
- Every project, character, scene, asset, job and credit record is looked up **scoped to the
  current user**. Someone else's ID returns **404**, so IDs cannot be probed.
- Admin endpoints use `@admin_required` on every route; changes are written to `audit_events`.
- Role changes and deactivation revoke the user's sessions.
- No default admin account or password exists; admins are created with `flask aszda create-admin`.

### Input and files
- Request bodies validated with pydantic; unknown fields are rejected (no mass assignment).
- Uploads: size limit (`ASZDA_MAX_UPLOAD_MB`, also enforced by Flask's `MAX_CONTENT_LENGTH`),
  type detected from file **content** (magic bytes), not from the name or browser header.
- Storage keys are generated by the server (`users/<uuid>/assets/<uuid>.<ext>`); user file names
  never reach the filesystem; local paths are checked to stay inside the storage root.
- Files are private. Access is through short-lived signed links (15 minutes by default).
- Served files get `Content-Security-Policy: sandbox` and `nosniff`.
- SQL is built with SQLAlchemy (parameterised); `LIKE` searches escape wildcards.

### Secrets
- All credentials come from environment variables. `.env` files are git-ignored; only
  `.env.example` with placeholders is committed.
- Provider API keys are used only on the server. Admin screens show **whether** a key is set and
  the variable name, never the value.
- Production refuses to start with weak/missing secrets, insecure cookies, in-memory rate limits,
  console email or eager jobs (`ProductionConfig.validate`).

### Abuse and cost control
- Rate limits (Flask-Limiter; Redis-backed in production) on sign-up, login, password reset,
  verification and job creation.
- Generation requires a verified email, enough credits, a configured price, and stays within
  per-job, concurrent, daily and monthly limits — all enforced on the server.

### HTTP hardening
`X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`,
`Cross-Origin-Opener-Policy`, a deny-all CSP on API responses, HSTS in production,
`Cache-Control: no-store` by default. CORS limited to `ASZDA_CORS_ORIGINS`.

### Errors and logs
Unexpected errors return a generic message with a reference ID; details go to server logs only.
Passwords, tokens and keys are never written to the audit log.

## Known gaps (to close before public launch)
- No multi-factor authentication yet.
- No automated malware scanning of uploads (type checks only).
- Email sending in production requires an SMTP provider to be configured.
- An external penetration test has not been done.
- Payment security requirements apply once payments are built (webhook signatures, idempotent
  processing, never storing card data) — see docs/CREDITS.md.
